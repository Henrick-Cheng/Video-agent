# Benchmark V2 Analysis — cooking.mp4

> 完整数据见 [docs/benchmark_v2_results.md](benchmark_v2_results.md)

## 核心结论

**去掉"可读字幕"干扰变量后，Agent 在时序推理上的优势从 v1 的 0.300 跃升至 0.600（+100%），同时整体上与 vlm_direct 差距从 0.180 缩小到 0.040。**

这直接验证了时序场景图（带 `first_seen` / `last_seen` 时间戳的三元组结构）的核心设计价值：在需要跨时间步推理的问题上，结构化工作记忆明显优于"直接看帧"的方式。

## 各方案表现分析

### Agent（0.313 ± 0.100）

**时序推理（0.600）是最大亮点**。"炒糖色在放猪肉之前"、"葱花是最后才加入"等问题，Agent 可以直接查询场景图的时间戳信息，精确回答跨步骤的先后顺序。相比之下 vlm_direct（0.367）只看静态帧，难以重建完整时间线。

**关系推理（0.367）同样领先**。"依次用了哪几种锅"需要理解 平底锅→炒锅→砂锅 这一完整使用链，Agent 通过多轮 query_scene_graph + inspect_frame 迭代逐步拼出答案。

**物体识别（0.233）和计数（0.100）偏低**，主要瓶颈是场景图仅 11 实体——这是 `build_scene_graph` prompt 未针对烹饪场景优化导致的，与架构本身无关。

### vlm_direct（0.353 ± 0.009）

物体识别最佳（0.600）：cooking.mp4 没有文字 UI，但 VLM 直接看帧可以识别葱花、五花肉、砂锅等视觉明显的物体。4 帧采样足够覆盖"看到什么"类问题。

时序推理（0.367）弱于 Agent（0.600）：静态帧无法编码操作顺序，VLM 只能猜测或凭常识。

### rag_only（0.113 ± 0.009）

全面偏低符合预期：场景图稀疏（11 实体），实体属性和计数类直接得 0.000。RAG-only 方案对场景图质量极为敏感，而当前构建 prompt 针对游戏场景优化，迁移到烹饪场景后覆盖率显著下降。

## v1 vs v2 对比：评测设计的重要性

v1（游戏录屏）中 vlm_direct 以 0.540 大幅领先，因为游戏 UI 上有可直读的队伍名称、角色名等文字。这让"直接看帧"获得了不公平的优势。

v2（烹饪视频）消除了这个变量：字幕均为喜剧评论风格（"苍蝇搓手"、"公文包"），不包含食材、步骤、顺序等信息。在公平对照下：

- vlm_direct 从 0.540 → 0.353（↓35%）
- agent 从 0.360 → 0.313（↓13%，更稳健）
- 两者差距：0.180 → **0.040**

**这说明 v1 的 vlm_direct 优势主要来自视频内容特性（可读文字），而非方法本身的推理能力。**

## 改进方向

**高优先级（修场景图构建）**：

将 `build_scene_graph` 的 prompt 增加烹饪专项指令："提取烹饪动作（切/炒/炖）、容器变化（食材从X锅转入Y锅）、火候变化，记录每步的时序先后"。预期效果：实体数从 11 → 25+，三元组从 9 → 40+，agent 整体准确率预计提升到 0.400–0.450。

**中优先级（增加帧数）**：8 帧均匀采样对 202s 视频每帧覆盖 ~25s，容易漏掉炒糖色（~15s）、加香料（~15s）等关键短暂步骤。建议预构建改为 16 帧。
