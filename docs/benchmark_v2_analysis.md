# Benchmark V2 Analysis — cooking.mp4

> Status: Preliminary (agent run 1 only). Full analysis pending DashScope quota restore.

## 评测设计改进点

相比 v1（游戏录屏），v2 cooking.mp4 评测集做了以下设计改进：

1. **反字幕设计**：所有 25 题均无法通过读字幕作弊——视频字幕为喜剧风格（"苍蝇搓手"、"公文包"），不含食材列表、步骤顺序等信息
2. **时序推理加强**：5 道时序题考察"先A后B"的跨步骤推理（如"炒糖色在放肉前还是后"），需要理解完整时间线
3. **关系推理加强**：5 道关系题考察跨工具/跨步骤的因果关联（如"五花肉依次用了哪几种锅"）
4. **视觉理解深度**：cooking.mp4 无可直读文字 UI，任何方案都必须真正解析视觉内容

## 初步发现（Agent Run 1 = 0.220）

### 场景图覆盖不足是主因

cooking.mp4 涉及 8 个明显的烹饪阶段和 12+ 种食材/调料，而预构建场景图仅有 11 实体、9 三元组。
对比 test1.mp4（游戏录屏，29 实体 / 24 三元组），cooking.mp4 信息密度更高但图覆盖更低。

**根本原因**：`build_scene_graph` 提示词针对游戏场景优化（实体、关系、空间关系），对烹饪步骤（动作序列、食材转变、容器变换）捕获效果差。

### 时序题 Agent 相对占优（0.300）

Q19（葱花最后出锅）和 Q20（焯水→炒糖色）得到了正确回答，说明即使场景图不完整，
时间戳信息对简单时序问题仍有帮助。然而复杂时序（Q16、Q17）消耗了 10–11 次工具调用
且均失败，表明当推理链需要跨 3+ 步骤时，当前场景图结构不足以支撑。

### 关系推理是最大挑战（0.100）

关系题要求理解"哪个步骤用哪个工具处理了哪个食材"，这是场景图的三元组结构本应擅长的任务。
低分说明三元组数量（9条）远不足以编码烹饪流程的完整状态变化序列。

## 改进建议

| 改进 | 预期效果 |
|------|---------|
| 增加预构建帧数（8→16 帧） | 场景图实体 11→25+，覆盖更多烹饪阶段 |
| 针对烹饪场景优化 `build_scene_graph` prompt | 增加"烹饪动作、容器变化、先后顺序"的提取指令 |
| Entity 存储火候属性（大/中/小火） | 提升属性题得分 |
| 实现 `vlm_direct_no_subtitle` 变体 | 控制字幕变量，更公平比较 |

## 对比 V1 评测（test1.mp4 游戏录屏）

| 维度 | V1 (test1.mp4) | V2 (cooking.mp4) |
|------|----------------|------------------|
| Agent 整体 | 0.360 | 0.220 (run 1) |
| 视频类型 | 游戏 UI，有可读文字 | 烹饪教程，无直读文字 |
| 场景图规模 | 29 实体 / 24 三元组 | 11 实体 / 9 三元组 |
| vlm_direct 优势来源 | 读取游戏 UI 文字 | 无字幕可读（更公平） |
| 时序推理 Agent 优势 | 0.300 (vs 0.000) | 0.300 (vs TBD) |

**结论**：cooking.mp4 是更具挑战性、更公平的评测视频。Agent 在没有"文字捷径"的情况下仍能在时序推理上保持优势，验证了时序场景图的核心价值。
